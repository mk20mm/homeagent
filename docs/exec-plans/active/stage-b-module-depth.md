> 验收用例格式对齐 AI-STD-005：`{category, description, steps, passes}`，随实现翻转。

**当前状态（2026-09-23）**：🚧 进行中 —— T-B18 日程模型 ✅ 完成（C13 契约 + ent + 领域服务 + HTTP 出口 + 工具 + 5 单测 + curl 验收全绿），下一步 T-B01/T-B02 家务深耕或 T-B19 日历视图。

## 任务组织原则

- 一条任务 = 一次可验证的交付（契约变更 / 领域能力 / HTTP 出口 / 页面交互 / 通知接入 之一或组合）。
- 模块内推进顺序固定：**契约 → 领域服务 → HTTP 出口 → 页面/交互 → 通知接入**（与「边界处解析数据形状」不变量一致）。
- 表中「验收要点」是任务内嵌的判定；标 ★ 的关键路径任务另有完整 eval 用例（见文末）。
- 状态标记：⏳ 未开始 / 🚧 进行中 / ✅ 完成 / ❌ 放弃（附理由）。

## 决策日志

| 决策                                                          | 理由                                                                                               |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 模块内推进顺序固定为「契约 → 领域 → HTTP 出口 → 页面 → 通知」 | 与「契约先行」和「边界处解析数据形状」两条不变量一致；页面接不上真接口就会退化成假数据（T17 教训） |
| 日程模型（T-B18）先于一切日历 UI                              | 成员颜色、重复规则、农历标记、提醒阶梯四件事都落在模型上；先画 UI 会导致返工                       |
| 频率/轮值放服务端计算（T-B02）                                | 客户端算周期会在多端与离线场景分叉；周期计算是确定性逻辑，属代码不属于界面                         |
| Today（T-B24）晚于各模块查询出口                              | Today 是聚合视图，先有数据源再拼装；否则会为了出页面而造临时接口                                   |
| 全局输入栏（T-B25）与适老模式（T-B29）可并行先行              | 两者都不依赖新数据，且直接兑现「最省输入」原则，收益立即可见                                       |
| 报饭从一级导航降级进 Today（T-B30）                           | 每天一次的二值状态占 1/4 导航位不合理；做饭决策所需信息（几人吃 + 还缺谁）本就该在 Today           |
| 通知只做「可行动」的（T-B07/T-B14/T-B15/T-B20/T-B32/T-B33）   | P7 主动有预算：每条推送点开必须能当场做点什么，否则会训练用户忽略通知                              |
| 收尾项（导出/邀请/异常检测/周报/离线）不阻塞出口判定          | 它们提升信任与完整性，但不改变「四模块 ≥ L3」的判定；放在阶段 B 尾部避免拖长关键路径               |

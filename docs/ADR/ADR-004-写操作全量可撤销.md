# ADR-004：所有写操作强制可撤销（编译期约束）

> 2026-10-01 适用范围修订：本 ADR 继续适用于可逆的本地数据写入；真实设备动作使用 [ADR-007](ADR-007-本地撤销与设备补偿.md) 的取消/补偿协议，不能称暂停为撤销清扫。以下保留原决策历史；新增接口尚未实施。

- **状态**：接受（设计阶段，Phase 03）
- **日期**：2026-09-15
- **决策者**：项目维护者
- **关联标准**：AI-STD-002（自治级别 / Rollback 要求）、AI-STD-007（R2+ 可逆内部写必须可回滚）

## 背景

家事 Agent 的核心价值是「说出口即落地」——用户说完一句话，账已记、任务已派、饭已报。但 AI 不是百分百可靠：

- 意图识别可能错（把「买菜花了 120」记成 1200）
- 参数抽取可能错（类别归错、人选错）
- 家庭成员可能改主意

**家庭场景里，钱的错误和任务误派最伤信任**（见 [AI-PRD.md §1.4](../AI-PRD.md) 失败成本）。传统软件的「确认弹窗」在对话入口里体验很差（每句话都要点确认），但如果执行后不可撤销，一次错误就可能造成实际损失。

## 决策

**所有写操作（A2/A3 级）强制可撤销**，且通过**编译期约束**保证，而非靠人工记得：

- 工具接口 `Tool` 中，写操作必须实现 `Undo()`，查询类不实现（接口层面区分，未实现则编译不过）
- undo 数据在工具执行成功后**同步写入** `undo_log`（与业务写同一事务/紧随其后），再回传 LLM
- 结果卡片默认带「撤销」按钮（高危操作必显，中危可选）
- undo_log 有效期 24h，cron 清理；撤销本身也写审计
- 支持**级联回滚**：如「记账+自动归类」组合操作，撤销时一并回滚关联数据

## 后果

### 正面后果

- **信任闭环**：「对话→执行→撤销」是一期 MVP 的核心验证目标，撤销让用户敢用、敢说
- **安全兜底**：A3 级（记账/改预算/删任务/改权限）即使执行错了，一键回滚，损失可控
- **审计完整**：撤销链路留痕，财务操作完整可查
- **降低 HITL 摩擦**：不必每个操作都弹确认（破坏对话体验），改为「先执行、可撤销」，仅高危对老人小孩开二次确认

### 负面后果 / 风险

- **实现成本高**：每个写工具都要写一份逆向逻辑，开发量翻倍
- **级联回滚的复杂性**：跨模块联动（菜谱→清单→记账）的回滚链路可能长，中间状态处理需小心
- **24h 有效期边界**：超时后用户想撤销会失败，需明确提示

### 缓解措施

- 编译期约束（接口必实现）杜绝「忘了写 undo」
- undo_log 与业务写在事务内，保证「要么都成、要么都不成」
- 级联回滚按 undo_data 存关联 ID，撤销时按记录的依赖顺序回滚
- 超时撤销返回明确状态（「该操作已超过 24 小时撤销窗口」），并引导人工处理
- Eval 强制覆盖：撤销链路成功率 ≥ 99%（[AI-PRD.md §6.1](../AI-PRD.md)）；高危操作无 undo = Critical 否决项

## 备选方案

| 方案                          | 为什么不选                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------- |
| **所有写操作执行前弹确认**    | 破坏「说出口即落地」的对话体验；家庭群里每句话都要点确认，没人愿意用         |
| **仅高危可撤销，中危不管**    | 打卡误派、报饭报错同样是高频误操作，不撤销一样伤体验                         |
| **靠 LLM 自己判断要不要回滚** | 违反 AI-STD-007「禁止把第二个 LLM 当唯一安全闸门」；确定性回滚必须由代码保证 |
| **人工后台改库兜底**          | 单家庭自用无运维人力，且手工改库无审计、易出错                               |

# ADR-003：数据层 SQLite 起步，ent 保平滑迁 Postgres

- **状态**：接受（设计阶段，Phase 03）
- **日期**：2026-09-15
- **决策者**：项目维护者
- **关联标准**：AI-STD-003（状态设计）、AI-STD-008（生产）

## 背景

单家庭自用，数据量小（成员个位数、账单/任务年量级万条以内），部署在单台 VPS。但项目设计上有长期演进预期：

- 数据要长期累积（多年账单、家庭历史），不能丢
- 未来可能多端高并发或数据量增长，需要能迁到更强数据库
- 会话状态、undo_log、审计日志都需要持久化

## 决策

- **起步用 SQLite**（单文件、零运维、随二进制部署）
- ORM 用 **ent**（schema 即代码、类型安全强、迁移友好）
- **不锁死 SQLite**：ent 的 schema 抽象使后续可平滑迁移到 **Postgres**

## 后果

### 正面后果

- **零运维**：单文件数据库，备份就是复制文件；Docker 部署只需挂载一个卷
- **性能足够**：单家庭量级下 SQLite 读性能优秀；写并发场景（家庭成员同时记账）用 WAL 模式即可
- **迁移路径清晰**：ent 生成的是供应商无关的 schema，换驱动即可迁 Postgres，业务代码基本不动
- **本地开发友好**：无需起数据库服务，`go test` 直接跑

### 负面后果 / 风险

- **写并发上限**：SQLite 写锁是库级（WAL 下读不阻塞写，但同时只有一个写者），高并发写场景会排队
- **水平扩展受限**：单机单文件，无法读写分离/分库
- **高级特性缺失**：无内置复制、无细粒度权限角色、时区/函数行为与 Postgres 有差异

### 缓解措施

- 开 WAL 模式 + 合理连接池配置
- 写操作天然幂等设计（见 [AI-PRD.md §3](../AI-PRD.md) 幂等键），并发重复写返回已存在而非重复入库
- **不在 SQL 层写死 SQLite 方言**：所有 schema 经 ent 定义，迁移时只改驱动配置
- 迁移触发条件（到时直接切 Postgres）：写并发出现明显排队 / 数据备份体量超过单文件管理舒适区 / 需要多端强一致性

## 备选方案

| 方案                   | 为什么不选                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| **直接上 Postgres**    | 一期就一台 VPS，起一个数据库服务增加运维成本与部署复杂度；单家庭量级性能过剩                |
| **MySQL**              | 生态成熟，但 ent 对 Postgres 支持更贴合现代特性；且与未来 iCal/时区等处理不如 Postgres 顺手 |
| **MongoDB**            | 文档型与「账单/任务/权限矩阵」这类强结构化领域不匹配，事务与一致性约束弱                    |
| **直接用文件/KV 存储** | 查询能力不足，审计/统计/撤销链路需要关系查询                                                |

# ADR-006：主动服务底座——站内静默通知 + 事件级幂等

- **状态**：接受（2026-09-22，T-A10 已落地并 e2e 验收通过）
- **日期**：2026-09-20
- **决策者**：项目维护者（产品决策已由维护者于 2026-09-20 给出，见「决策」）
- **关联标准**：AI-STD-002（确定性边界）/ AI-STD-006（仓库 Harness）
- **关联计划**：[stage-a-credibility-base.md](../exec-plans/active/stage-a-credibility-base.md) T-A10（C4/C5）

## 背景

产品理念的第一条承诺是「系统跑腿」——到点提醒、缺口催办、账单到期、耗材预警。当前实现度 0：`internal/` 无调度器、无通知、无定时任务（`robfig/cron` 连依赖都不在 `go.mod`）。这是阶段 B 四模块深耕（日程提醒阶梯 / 周期账单 / 缺口催办）的唯一共同前置（`product-inspiration-01.md` 判断 I3）。

主动服务最容易翻车的地方是**打扰**：提醒太多 → 全关掉 → 再也不打开。因此在动代码前必须先定「怎么打扰」。

维护者于 2026-09-20 明确了产品取向（原文要点）：**「提醒一次就好了，有通知数量就好，超过 99 个显示 99+，参考微信。为什么还要声音？」**——即：**不要声音、不要震动、只要未读计数**。这一句把「打扰预算」问题大幅简化：没有声音与震动，就没有"打断用户"这回事，通知退化为**用户主动来看**的信息。

## 决策

**通知只做站内、静默、事件级幂等，不做声音/震动/浏览器推送。** 五条：

1. **渠道：仅站内**。铃铛角标（未读计数）+ 通知中心抽屉（一处回溯全部推送）。不做浏览器推送、不做短信、不做邮件（V2 再评估推送）。
2. **零声音、零震动**。通知是"用户想起来时去看"的东西，不是"打断用户"的东西。因此：
   - **不需要免打扰时段**（没有声音可在夜间打扰）
   - **不需要按类型静音**（没有哪一类会吵）
   - `mute_preference` 表**不建**（YAGNI；若将来加推送再加）
3. **事件级幂等：同一事件只生成一条通知**。唯一键 `(type, ref_id, member_id, scheduled_at)`；调度器每分钟重复扫描不会刷屏。
4. **未读计数微信式**：角标显示未读数，**超过 99 显示 `99+`**；打开通知中心不自动全部已读（需显式操作，避免"瞄一眼就没了"）。
5. **可行动 + 权限裁剪**：每条通知带 `action_label` / `action_path`，点开跳到可当场操作的页面；通知内容按成员权限裁剪（孩子不见他人账单金额），行动链接仍受 ADR-005 双保险约束（点了也做不了越权事）。

### 数据模型（新增 1 张表）

```
notification: id(UUID) / member_id / type(enum: task_due·chore_overdue·meal_gap·
              bill_due·budget_over·report) / title / body / ref_type / ref_id /
              action_label / action_path / read_at(nullable) / created_at
              唯一键 (type, ref_id, member_id, scheduled_at) → 幂等
```

- `read_at` 为空 = 未读；角标数 = `COUNT(*) WHERE member_id=? AND read_at IS NULL`，前端封顶 `99+`
- 通知内容只存"结论 + 依据指针"（`ref_type`/`ref_id`），金额等敏感字段**不在通知里冗余**，点开按权限实时查

### 调度器

`robfig/cron` 每 1 分钟 tick → 扫到期项 → 查幂等键 → 生成通知（静默入库）。阶段 A 只接两个源：**任务到期**（`tasks` 的 `due_date`）与**报饭缺口**（当日未申报成员，16:00 后生成）；周期账单/日程提醒阶梯在阶段 B 接同一底座。调度误差 ≤ 1 分钟（`AI-PRD §10.11`）。

## 后果

### 正面后果

- **打扰问题被结构性消解**：零声音零震动 = 任何时候都不打断用户，P7（主动有预算）自动满足，无需复杂的免打扰配置
- **实现面大幅收窄**：一张表 + 一个 cron + 一个抽屉页面，`mute_preference` / 静音时段 / 推送 token 续期全部不做
- **幂等键保证不刷屏**：调度器重复执行安全（同一事件只一条），天然支持无状态重启
- **可回溯**：通知不删除（软清理），审计与"上周提醒过我"的争议可查
- **阶段 B 直接复用**：日程提醒阶梯、周期账单到期、缺口催办都只是"新增 type + 新增扫描源"

### 负面后果 / 风险

- **不看就没有**：纯站内意味着用户不打开 App 就不知道"纸巾快用完了"。这是 V1 的有意识取舍——产品当前阶段全家都在日常使用（报饭/打卡/记账是每天的动作），Today 首页与角标即触点；真正需要"人不在 App 里也要找到他"时（如缴费逾期），再加推送
- **角标焦虑**：未读数堆到 99+ 会变成新的心理负担。缓解：通知中心默认按类型折叠；关键通知（账单到期）7 天后自动归档不计入未读
- **没有提醒强度的分级能力**：所有通知"生而平等"。若将来证明"账单到期该比报饭缺口更强地触达"，需要补推送或置顶机制（V2 评估）

### 缓解措施

- 通知保留 `type` 枚举，将来加静音/分级只需加字段，不改模型骨架
- 调度器做成 Provider 接口（同 `Notifier` 横切关注点约定），阶段 B 加源不动核心
- evals（T-A11）覆盖：通知内容不泄漏无权数据（safety 否决项）

## 备选方案

| 方案                                    | 为什么不选                                                                                               |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **浏览器推送（Web Push）**              | 自部署需管 VAPID key、跨浏览器兼容、token 续期与失效；V1 全家日常在用 App，站内触达足够，ROI 不足。留 V2 |
| **声音/震动 + 免打扰时段 + 按类型静音** | 维护者明确不要声音 → 打扰的前提不存在；三套配置（时段/类型/偏好）为不需要的问题付复杂度                  |
| **只在 Today 首页展示，不做通知中心**   | 无法回溯（"昨天提醒过我吗"无处可查）；且角标是"有事"的唯一跨页触点，不做就退回"用户自己想"               |
| **用 LLM 生成通知文案**                 | 违反确定性边界（`AI-PRD §3`）：通知是确定性的定时行为，文案用模板 + 数据拼接，不赌模型                   |

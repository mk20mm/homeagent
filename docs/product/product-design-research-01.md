## 1. 产品理念

### 1.1 产品是什么（一句话）

> 帮助【**承担家庭运营角色的那个人**（家长/家务总管）】，在【**做饭中、通勤中、出门前、月底对账**这类双手被占、时间碎片化的场景】下，通过【**一句话触发 AI 调度后端工具（记账/报饭/派任务/打卡/查预算/推荐晚餐）**】，更高效地完成【**把家务、用餐、账单办到位，并让全家人共享一份可信的家庭事实源**】。

### 1.2 产品为什么存在

**用户现在怎么解决**（`AI-PRD §1.2` 的落地复述）：

| 事项 | 现状方式                             | 现状的代价                            |
| ---- | ------------------------------------ | ------------------------------------- |
| 记账 | 群里说一句 / 纸质账本 / 多个记账 App | 人工漏记率 30%+，月度对账 30 分钟以上 |
| 报饭 | 群里接龙或挨个问                     | 汇总 5–10 分钟，常有人漏回            |
| 家务 | 吼一声 / 谁看谁做                    | 平均需 2–3 次提醒才有响应             |
| 日程 | 各自手机日历 + 群里喊                | 农历生日、缴费/体检到期会忘           |
| 囤货 | 想起来才买                           | 卫生纸/米面总是用完才发现             |

**现有方式的问题不是"功能不够"，而是三重成本叠加**：① **入口成本**——每件事一个独立 App，打开成本高于事情本身价值，于是"不记了"；② **汇总成本**——信息散在群里，收集方（做饭的人、管账的人）要人工收口；③ **维护成本**——没有人在长期维护家庭数据，谁记谁累。

**这个产品真正想改变的**：**把家庭事务的录入成本压到接近零，让家庭第一次长期拥有一份所有人共享、可核对、可撤销的单一事实源。** 这不是"多一个记账工具"，而是把"家庭运营"从**人肉维护**变成**系统维护**。

理念与现实的第一处落差：`AI-PRD §1.3` 的"不是非 AI 不可的部分"一段说得很清楚——纯规则系统也能做记账/清单/日历，**AI 的不可替代性在"对话即入口"与"跨模块联动编排"**。但当前的跨模块联动（菜谱→清单→记账、日程→提醒）全部是二期/未进契约，主动服务（跑腿）零实现。**产品的差异化论证是"编排与主动"，实现是"理解与执行"**，中间那段就是本文要补的设计。

### 1.3 产品核心价值（3 条，按不可替代性排序）

1. **把录入成本降到"一句话"**。价值不在"AI 记账更准"，而在"记这个动作不再需要被权衡、不需要先打开哪个 App"。**用户收益：省操作成本 + 学习成本**（这是唯一非 AI 不可的价值）。
2. **一份所有人共享、可核对、可撤销的事实源**。取代群聊碎片与人脑记忆，让"我以为对方做了"和"这笔到底记了没"从对话框里消失。**用户收益：省沟通成本 + 错误成本**。
3. **数据反过来替人盯着人**。未申报催办、超支预警、耗材将尽、一次汇总把一周的事收口——产品替用户承担"记得"和"盯着"这两件最耗神的事。**用户收益：省判断成本 + 记忆成本**。

> 第 3 条是 README「核心特性 · 主动服务」的原文承诺，也是当前实现落差最大的一条（判断 D1）。它不是"锦上添花"，而是本产品能否从"工具"变成"住在家里的助手"的分水岭。

### 1.4 定位声明与模块深耕矩阵（2026-09-18 校正）

**定位声明**：本产品是**家庭事务中枢**（Household Hub），**不是记账应用**。家务、用餐、账单、日程四个模块在身份上**同权**——记账只是其中之一，它做得再深也不构成产品本体。

| 模块 | 一期定位（同权）                            | 常见误解（要避开）       |
| ---- | ------------------------------------------- | ------------------------ |
| 家务 | 派单 / 打卡 / 例程 / 频率 / 轮值 / 缺口催办 | "就是一个待办清单"       |
| 用餐 | 报饭 / 缺口 / 推荐 / 菜谱→缺食材            | "附属在记账里的外卖记账" |
| 账单 | 记账 / 预算 / 周期账单 / 统计               | "产品的主体"（错）       |
| 日程 | 共享日历 / 提醒 / 农历 / 纪念日             | "以后再说"（错）         |

**模块深耕矩阵**（深度分级 L0–L4 见 [`product-inspiration-01.md`](product-inspiration-01.md) §3.0）：

| 模块 | 现状                                                  | V1 目标  | 差距的关键件                                                   |
| ---- | ----------------------------------------------------- | -------- | -------------------------------------------------------------- |
| 家务 | L0（假数据，打卡无响应）                              | **≥ L3** | handler、频率与周期、轮值、例程、缺口催办                      |
| 用餐 | L0（假数据，刷新即丢）                                | **≥ L3** | handler、未申报缺口、例外申报、菜谱→清单（最小版）、推荐给依据 |
| 账单 | L2（真实数据 + 修正 + 撤销，缺分组/搜索/周期/预算页） | **≥ L3** | 按日分组+每日小计+补账、多维搜索、周期账单、预算提醒           |
| 日程 | 不存在（模块未进契约）                                | **≥ L3** | 日程数据模型、成员颜色、重复规则、提醒阶梯、农历               |

**为什么两条决定必须一起下**：V1 若只把某模块做深，产品会被固化成"记账/家务工具"，之后再挂模块就像打补丁；V1 若四模块齐但都浅，就不构成中枢。**同权 + 每模块 ≥ L3** 是唯一自洽的 V1 形态。

> **连带结论（关键）**：日程模块依赖提醒与调度能力，因此**主动服务底座（C4/C5）从原 Phase 2 前移到 V1 阶段 A**；否则日程只能做成"看日历"，等于没深耕。完整推导见 [`product-inspiration-01.md`](product-inspiration-01.md) §6。

## 2. 产品设计原则

理念（动嘴，系统跑腿）翻译成 8 条可执行的设计规则。每条都是**判断标准**，而不是口号：出现分歧时用它裁决。

### P1 · 最省输入：任何新录入路径的成本必须 ≤ 现状

- **为什么符合理念**：理念的第一性原理是"家人不需要学一个管理系统，只需要会说话"。任何比现状更贵的路径都在违背它。
- **对功能设计意味着什么**：每个模块必须定义自己的"最省输入路径"（对话 / 一键 / 默认值三选一，取最省者）；**新增采集字段前先问：能不能不采？能不能推断？**
- **对交互设计意味着什么**：默认值优先于输入框；能从上下文推断的绝不发问；报饭、打卡这类二值动作必须是**一次点击**，不是一句话。

### P2 · 无孤岛：说的和看的是同一份数据

- **为什么符合理念**：用户心里只有一个"家事本子"，不在乎是说的还是点的。任何"说了但页面不变"都是 bug 级体验（`ux-exploration-01` 断点级结论）。
- **对功能设计意味着什么**：工具与其查询出口**同批交付**——禁止"只写工具、不写页面数据源"（当前家务/报饭正是这个错配）。
- **对交互设计意味着什么**：卡片与页面实体是同一份数据的两个视图；卡片必须带"在账本/任务/报饭中查看"跳转（记账页已实现 `?focus=` 高亮，应成为通用模式）。

### P3 · 纠正优先于撤销：改比删便宜

- **为什么符合理念**：AI 的价值是省事；"错了只能整笔撤销重说"比原来更费事，用户会退回旧方式。
- **对功能设计意味着什么**：每个高频实体必须**同时**有 `Undo`（已有，ADR-004）与 `Update`（目前只有 expense 有 `PATCH /expenses/{id}`）；两者都要落 `undo_log`。
- **对交互设计意味着什么**：卡片/列表项上"改"是一等公民（Inline Edit），"撤销"是兜底；改完仍然可撤销（回滚到修改前，已由 `update_expense` 隐藏工具实现，应推广到任务/报饭）。

### P4 · 默认优先，例外申报：系统先替人想，人只做否决

- **为什么符合理念**："用户需要想的越来越少"最直接的落点就是**少问一次**。
- **对功能设计意味着什么**：报饭按历史规律给默认值、分类按上次记忆、金额给候选、常用任务给模板；只有"与默认不同"时才需要用户动作。
- **对交互设计意味着什么**：一键确认优于填空；"不用报"优于"记得报"；默认值必须可见可改（不能悄悄替用户决定）。

### P5 · 先确认后执行：不确定的事不先落库

- **为什么符合理念**：涉钱涉责任的事，信任来自"可核对"，不是"事后可撤销"。
- **对功能设计意味着什么**：置信度分级 + 门槛触发两阶段提交（低置信度先不入库）；`AI-PRD §4` 的 A3 Preview + Confirm 从"大额"扩展到"歧义"（"花了十来块"）。
- **对交互设计意味着什么**：确认卡必须**可编辑**（不只是对/不对），**确认成本必须 ≤ 修正成本**，否则用户宁愿让它错。

### P6 · 缺口显式：没完成的部分是产品的一部分

- **为什么符合理念**：家庭协作的真实痛点从来不是"已收集的"，而是"还缺谁的"——做饭的人不知道还差谁没报，管账的人不知道谁没打卡。
- **对功能设计意味着什么**：所有收集类模块（报饭/打卡/清单）的接口必须返回缺口（未申报/未完成/未认领名单），而不只是已完成项。
- **对交互设计意味着什么**：缺口与"一键催办"必须相邻显示；缺口是**待办态**，不是异常态，视觉上要温和（不做公开点名排名）。

### P7 · 主动有预算：可以打扰，但必须可静音、可追溯

- **为什么符合理念**：理念承诺"不用主动打开就有"。但主动服务最容易变成骚扰，因此打扰本身要成为被设计的对象。
- **对功能设计意味着什么**：通知中心（一处可回溯全部推送）+ 提醒频道 + 免打扰 + 只推"可行动的"（每条推送点开必须能当场完成动作）。
- **对交互设计意味着什么**：每条推送都带上下文（谁、什么事、现在能做什么）与静音开关；不允许"无法关闭的提醒"。

### P8 · 复杂在系统，界面只留下一步

- **为什么符合理念**：家人不学管理系统 → 一级界面只呈现"当前要做什么"，高级能力（模型/权限/审计/用量）降级到二级或管理端。
- **对功能设计意味着什么**：面向家人的入口不出现"配置""权限""参数"这类词；管理能力默认只在 admin 端。
- **对交互设计意味着什么**：一级导航只放家庭日常事务；每个页面顶部一行"现在该做什么"；AI 的判断必须带"依据"入口（可解释、可追溯），而不是一个不可质疑的结论。

## 3. 核心用户

| 角色                                    | 真实目的                                               | 使用频率与设备                  | 真正的障碍（不是功能缺失）                                           |
| --------------------------------------- | ------------------------------------------------------ | ------------------------------- | -------------------------------------------------------------------- |
| **运营者（parent）** 管账/派活/决定做饭 | 少花时间在"收口"上：知道钱花哪了、谁还没做、今晚做多少 | 每天 5–10 次，手机为主、碎片    | 现状里他得不到任何汇总——数据记进去了，但没人替他收口                 |
| **高频轻用户（老人）** 报饭 + 打卡      | 完成两个动作，别被打扰                                 | 每天 1–2 次，手机、字小、怕点错 | **登录令牌**与**打字**（`ux-exploration-01` 断点 1/2）；不是功能缺失 |
| **受限用户（小孩）** 看任务、打卡       | 知道自己该干什么                                       | 每天 1–3 次，手机               | 没有"我的任务"焦点视图；权限拒绝提示不解释原因                       |

结论：**产品的真实用户是运营者，但产品的价值网络依赖老人的报饭与小孩的打卡**——所以"降低他们的录入门槛"与"让运营者收口"是同一件事的两面。

## 4. 核心任务

**高频任务（每天多次，决定留存）**

1. 记账一笔（3–5 次/天）——已闭环（对话 + FAB + 修正）
2. 报饭一次（1 次/天）——**页面假数据，未闭环**
3. 打卡（1–3 次/天）——**按钮无响应，未闭环**
4. "我还有啥活"——工具存在（`list_my_tasks`），无页面焦点视图
5. "今晚吃啥"——工具存在（`suggest_dinner`），无页面入口

**关键任务（决定产品价值是否成立）**

1. 一句话把事办成（对话→执行成功率 ≥ 85%，`AI-PRD §1.4`）
2. 让做饭的人不必挨个问（报饭汇总 + 缺口）
3. 月底知道钱花在哪（`GET /expenses/summary` 已实现，UI 只显示一个总数）
4. 别人没做的事能被催（**当前完全不存在**）
5. 全家人都愿意用（周活跃 ≥ 80%，`AI-PRD §1.4` 的生死线——**当前老人门槛未解决**）

**低频但高风险任务**（六个，当前没有一处"统一可见、可追溯"的入口）

| 高风险任务             | 现状能力                                           | 风险                                                          |
| ---------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| 撤销（含撤销别人做的） | 只能点对话里那张卡片上的按钮，24h 窗口             | 卡片滚走后无入口；对话里说"取消刚才那笔"LLM 无工具（T-e2e-2） |
| 改账单金额/类目        | `ExpenseCard` Inline Edit + `PATCH /expenses/{id}` | 只能改最近可点到的那笔                                        |
| 删除会话/任务          | 会话有软删除 + 二次确认                            | 无批量、无回收站                                              |
| 改成员权限             | **admin 端只读占位**（T4），权限硬编码在种子数据   | 改权限 = 改代码 + 重部署                                      |
| 改模型/密钥            | admin 写端点已通，parent 双保险                    | 入口在 admin，家人端无说明                                    |
| 导出数据               | **不存在**（AI-PRD V2 才规划）                     | 数据在别人的 VPS 里，无安全感                                 |

## 5. 用户旅程（End-to-End）

### 5.1 现状旅程

| 步骤     | 用户目标               | 现状实际发生                                                 | 断裂点                                               |
| -------- | ---------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| 进入产品 | 快速开始               | 登录（**令牌不知从哪来**）→ 落地页是空白对话或恢复的最近会话 | 无"今天家里什么样"                                   |
| 理解状态 | 知道现在该干什么       | 数据散在 4 个 tab，其中 2 个是假数据                         | 无状态可理解                                         |
| 发现任务 | 知道有哪些事           | **完全缺失**：无通知、无未申报、无待办提醒                   | 用户必须自己想起来                                   |
| 执行操作 | 又快又省事地办         | 必须切到对话 tab、组织完整句子、等流式回复                   | 高频动作被低频交互拖累（`ux-exploration-01` 机会 1） |
| 系统处理 | 知道在做什么、进度如何 | 只有逐字 token；无"正在记账…"状态流；长任务不能后台化        | 等待不可控                                           |
| 查看结果 | 核对是否正确           | 卡片给出数据 + 撤销                                          | 无依据解释、无下一步                                 |
| 继续处理 | 顺手办下一件           | 无引导，用户自己回忆                                         | 无牵引                                               |
| 完成目标 | 收口、复盘             | 无日结、无周报、无"这周家里怎么样"                           | **旅程在"完成"处终止**                               |

### 5.2 理想旅程（本产品的 End-to-End 应该长这样）

| 步骤     | 产品提供什么帮助                                                                      | 归属主脉  |
| -------- | ------------------------------------------------------------------------------------- | --------- |
| 进入     | **Today 页给结论**：今晚 N 人在家（还缺 M 人）/ 我的待办 N 件 / 本月已花 X（预算 Y%） | 可见      |
| 理解状态 | 一行"现在该做什么"+ 家庭动态流（谁报了饭、谁打了卡、记了多少）                        | 可见      |
| 发现任务 | 通知中心 + 缺口条主动告知；未申报者点一键催办                                         | 跑腿      |
| 执行     | **任何页面底部都能说一句话**（全局输入栏）+ 快捷 chips（0 输入：报饭/打卡/记一笔）    | 输入      |
| 系统处理 | 状态流：识别中 → 执行中 → 完成；长任务后台化，完成后通知（可离开页面）                | 输入/跑腿 |
| 查看结果 | 卡片可**就地编辑**、可看**依据**、可"在 X 中查看"、可撤销                             | 可见      |
| 继续处理 | 下一步推荐（"还有 2 个任务没打卡""今晚 3 人吃饭，建议做 4 人份"）                     | 跑腿      |
| 完成目标 | 日结/周报把一周收口；重复事项"再来一次"一键复现                                       | 跑腿      |

**这处断裂为什么致命**：家庭事务是**永远重复**的。产品在"完成"之后不再出现，等于把留存交给用户的自律——而用户的自律正是这个产品要取代的东西。

### 6.2 当前优势（这是资产，不要推翻）

1. **契约驱动**：OpenAPI → oapi-codegen + openapi-typescript，前后端类型同源；改接口先改契约已成立。

## 8. 信息架构

### 8.1 现状 IA 与问题

```
TabBar（4）：对话 | 家务 | 记账 | 报饭         /settings（无入口）
```

三个结构性问题：

1. **对话被做成了"一个页面"**。后果：在记账页想记一笔必须切回对话——这正是"记账路径太重"的根因（`ux-exploration-01` 机会 1）。对话本质是**输入方式**，不是内容分区。
2. **报饭占了一等位置**，而更高频的"今晚吃啥"、更高价值的"今天家里怎么样"没有位置。
3. **管理能力（设置）没有入口，却和家庭能力混在同一层**——家人端既看到不该看的（供应商配置），又找不到该用的（退出登录之外的任何东西）。

### 8.2 建议 IA

```
Today（今天） ← 默认落地页
  ├─ 今晚吃饭     N 人在家 · 还缺 M 人 → 一键催办
  ├─ 我的待办     任务 + 打卡（一键）· 空则给可点示例
  ├─ 本月         已花 X / 预算 Y（点击下钻到记账）
  └─ 家庭动态     谁报了饭、谁打了卡、记了多少（可点开/可撤销）

事务（Things） ← 家务 +（V2）购物清单 +（V2）日程，同构收敛，不再新增 tab
记账（Money）  ← 流水 / 筛选 / 搜索 / 分类统计（含修正与撤销）
家庭（Family） ← 成员、邀请、我的设置、通知偏好；管理面（模型/权限/审计/用量）只从 admin 进
────────────────────────────────────────────
全局：底部常驻输入栏（任意 tab 一句话办事） + 通知铃铛（Today 头部）
对话历史：既有抽屉（侧边栏），不作为一级分区
```

**两条反直觉判断，及完整理由链**

| 判断                                 | 理念 → 问题 → 原则 → 方案 → 收益                                                                                                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **对话不该是 tab，应该是常驻输入栏** | 理念"动嘴就办成" → 问题：想办事却要先导航到对话页，高频动作被低频交互拖累 → P1 最省输入 + P8 复杂在系统 → 方案：底部输入栏全局常驻，对话历史收进抽屉 → 收益：任何页面记一笔/报饭都是 0 次导航（省**操作成本**）                                              |
| **报饭不该占 tab，应并入 Today**     | 理念"不用学管理系统" → 问题：一个每天一次的二值状态占据 1/4 导航位，而做饭决策所需信息无位置 → P1 + P6 → 方案：报饭成为 Today 的一张卡片 + 快捷 chip，汇总与缺口一并展示 → 收益：做饭的人一眼看到"几人吃 + 还缺谁"（省**沟通成本**），导航位让给"今天怎么样" |

### 8.3 信息可见性分层

| 层级          | 内容                                           | 理由                                                   |
| ------------- | ---------------------------------------------- | ------------------------------------------------------ |
| **始终可见**  | 输入栏、通知铃铛、当前页核心结论（一行）       | 用户任何时刻都能"说一句"与"知道有事"                   |
| **默认展示**  | Today 四块、账本流水与汇总、我与家人的任务状态 | 高频决策所需                                           |
| **渐进展示**  | AI 依据、审计明细、用量、模型差异、任务历史    | 低频、需上下文才有意义（P8）                           |
| **隐藏/隔离** | 供应商密钥、权限矩阵、系统配置                 | 只属于 admin；家人端不得出现（既减少噪音也减少误操作） |

## 9. 交互设计

### 9.1 Product Interaction System（统一交互规则表）

全产品所有页面必须遵守同一套语义——这是"一致性"最可落地的形式：**同类动作给同类反馈**。

| 动作类型   | 统一交互                                      | 现状差距                                                      |
| ---------- | --------------------------------------------- | ------------------------------------------------------------- |
| 写操作成功 | 结果卡片 + 撤销按钮 + "在 X 中查看"           | 已有（记账）；需推广到任务/报饭                               |
| 纠正       | 卡片/列表项**就地编辑**，保存后仍可撤销       | 已有（记账）；任务/报饭缺失                                   |
| 收集类     | 顶部缺口条："还缺谁 N 人" + 一键催办          | **完全缺失**                                                  |
| AI 判断    | 结论旁"依据"入口                              | **完全缺失**                                                  |
| 危险操作   | Preview + Confirm（**可编辑**）               | 约定存在，未普遍落地                                          |
| 长任务     | 状态流"识别中→执行中→完成" + 完成通知         | 仅有逐字 token                                                |
| 加载中     | 骨架屏（不用转圈）                            | MoneyPage 有 loading 态，其余无                               |
| 空状态     | **可点示例**（一次点击 = 一次教学）+ 一句引导 | 灰字不可点（走查断点 3）                                      |
| 失败       | 原因 + 重试 + trace_id，禁止静默吞错          | 多处 catch 后静默（`CONVENTIONS-frontend §6` 已禁止，需审计） |
| 高风险越权 | 拒绝 + 说明原因（谁没权限、找谁能开）         | 提示"无权限调用此工具"，不解释                                |

### 9.2 是否减少上下文切换

| 场景             | 现状跳转                            | 目标                                                                            |
| ---------------- | ----------------------------------- | ------------------------------------------------------------------------------- |
| 记一笔           | 对话页 → 说 → 看卡片 → 去记账页核对 | 任意页 FAB/输入栏 → 卡片就地 → "在账本中查看"高亮定位（已实现，需成为通用模式） |
| 撤销             | 翻对话历史找卡片                    | 撤销中心一处可见                                                                |
| 看家里发生了什么 | 4 个 tab 各看一遍                   | Today 动态流一屏                                                                |
| 改 task 执行人   | 无法改（无 Update）                 | 任务卡片 Inline Edit                                                            |

### 9.3 是否减少输入

- **能推断就不问**：报饭默认值（P4）、分类记忆、金额候选。
- **能点就不说**：快捷 chips、可点空态示例、二值动作按钮（报饭/打卡）。
- **能复用就不重复**：任务模板、最近使用、"再来一次"。
- **能指代就不复述**：记完 5 秒内说"改 130"直接改上一笔（上下文指代，见 §13 惊喜点 4）。

### 9.4 是否减少等待

| 现状                               | 目标                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------- |
| 只有逐字 token，不知道 AI 在干什么 | 状态流：识别意图 → 调用工具（显示工具名，如"正在记账…"）→ 完成          |
| 长任务必须留在页面等               | 后台执行 + 完成通知（P7）；用户可切页继续做别的事                       |
| 失败/断线输入丢失                  | 草稿自动保存 + 重连自动重发（`CONVENTIONS-frontend §8` 已约定，未实现） |
| 看不到历史消息加载态               | 分页加载更多（会话/账本）                                               |

### 9.5 状态与异常设计（统一清单）

| 状态           | 设计                                    | 关键要求                                       |
| -------------- | --------------------------------------- | ---------------------------------------------- |
| Loading        | 骨架屏 + 明确"在做什么"                 | 超过 1.5s 必须说明（NFR: 首 token P95 < 1.5s） |
| Empty          | 一句引导 + **可点示例** + 一个主按钮    | 空态是最好的教学位                             |
| Error          | 原因（业务语言）+ 重试 + trace_id       | 区分"令牌错误/过期/无权限/网络"                |
| Offline        | 顶部条"已离线，消息稍后发送" + 草稿保留 | 移动端高频（通勤/菜市场）                      |
| 缺口（待办态） | 温和提示 + 一键催办                     | 不是错误态，不点名批评                         |
| 成功           | 轻反馈 + 可撤销 + 下一步引导            | 轻提示不要挡住内容；**必须有下一步**           |

## 10. AI 产品能力

判据（沿用你的要求）：**AI 的价值以"减少了用户的一次操作"计价**，而不是"这里能不能塞个 AI"。

### 10.1 AI 应该出现的地方

| 能力                     | 具体场景                                                                   | 减少什么                     |
| ------------------------ | -------------------------------------------------------------------------- | ---------------------------- |
| **Understand** 理解      | "花了十来块"→ 候选金额并澄清；"这个月花在哪"→ 分类摘要而非数字；归类给依据 | 判断成本                     |
| **Generate** 生成        | 周报、菜单、购物清单、任务模板草稿                                         | 操作成本                     |
| **Recommend** 推荐下一步 | "你还有 2 个任务没打卡""今晚 3 人吃饭，做 4 人份""预算还剩 ¥120"           | 判断成本                     |
| **Detect** 主动发现异常  | 重复记账、金额异常、连续超支、长期未打卡、耗材将尽                         | 错误成本（当前**完全没有**） |
| **Execute** 执行         | 已有 ReAct 工具循环（危险分级 + 幂等 + 撤销 + 审计）                       | 操作成本                     |
| **Verify** 验证结果      | 低置信度先确认；执行后自检"我记的是 ¥120 食材，对吗"                       | 错误成本                     |

### 10.2 AI 不应该出现的地方

| 不该出现                                       | 理由                                                  |
| ---------------------------------------------- | ----------------------------------------------------- |
| 通用闲聊、陪聊                                 | `AI-PRD §7` 明确不做；家庭事务产品不靠情感陪伴获客    |
| 用 LLM 算钱 / 定权限 / 决定撤销窗口 / 判定幂等 | `AI-PRD §3` 确定性边界；这些必须留在代码里            |
| 报饭这类二值无歧义场景强制走对话               | 按钮比说话快（P1 反例：这里塞 AI 反而增加操作）       |
| 把对话当作**唯一**输入方式                     | 老人、静音场景、单手场景必须保留点按路径（P1 的兜底） |
| 无依据的自动推断（悄悄改用户数据）             | 违反 P5/P8；推断结果必须可见、可改、可撤销            |

### 10.3 AI 减少哪些工作（汇总）

| 工作 | 现状由谁承担                 | 应交给 AI                        |
| ---- | ---------------------------- | -------------------------------- |
| 输入 | 用户逐字打                   | 快捷 chips / 默认值 / 上下文指代 |
| 决策 | 用户想"今天吃什么""做多少"   | 推荐 + 依据 + 缺口汇总           |
| 记忆 | 用户记"谁没报饭""账单快到期" | 提醒 + 缺口 + 周报               |
| 核对 | 用户自己怀疑"记对了吗"       | 依据 + 撤销中心 + 审计           |

## 12. 产品差异化

### 12.1 别人有，我们能做得更好

| 维度 | 别人怎么做                     | 我们能更好在哪                                                                   | 依赖              |

### 12.2 别人没有，但用户真正需要

1. **家庭单一事实源**：对话/卡片/页面同源同改——"说一句"与"点一下"改的是同一份数据（P2）。
2. **撤销中心**：把 ADR-004 承诺的 24h 可撤销窗口变成**一处可见的入口**，而不是"记得那张卡片在哪"。
3. **缺口作为一等公民**：未申报/未打卡/未认领/未归类，四类缺口统一在设计语言里出现。
4. **老人小孩的零门槛入口**：邀请加入 + 大按钮一键动作（`elderTokens` 已备，只差落地）。
5. **跨模块联动**：菜谱→缺食材→购物清单→记账勾选→自动入账（二期护城河，当前未进契约 ⚠️）。

## 14. Ideal Product（如果今天从零设计）

一句话：**Today 是家，输入栏是嘴，事实源是账本，通知是闹钟，管理面与家人彻底隔离。**

```
┌─ 输入层：常驻输入栏（对话是"输入法"，不是页面）
│    任何页面能说一句话、也能点一下；结果就地成卡片，可改可撤可跳转
├─ 表层：Today（今天）
│    进来就知道：今晚几人吃 / 还缺谁 / 我要做什么 / 本月花到哪了 / 家里发生了什么
│    1–2 个动作完成今天的事，有缺口就催
├─ 数据层：家庭单一事实源
│    事务 / 账 / 用餐（+日程、购物 V2）——每个实体可编辑、可撤销、可追溯、可订阅
├─ 通知层：主动服务
│    到点提醒 / 缺口催办 / 超支预警 / 耗材将尽 / 周报——有预算、可静音、可追溯
└─ 管理面：admin（权限 / 模型 / 审计 / 用量）
     家人永不进入；模型与权限不再出现在家人端一级界面
```

**AI 的角色重新定义**：不是聊天机器人，而是**家庭事务的默认操作者**——

- 负责：理解意图、推断默认值、执行工具、发现异常、汇总收口、解释依据；
- 不负责：算钱、定权限、决定打扰时机与撤销窗口（确定性边界，`AI-PRD §3`）。

**与现状的差异（只列结构性差异）**

| 维度   | 现状                | Ideal                         |
| ------ | ------------------- | ----------------------------- |
| 落地页 | 空白对话            | Today（结论 + 缺口 + 动态）   |
| 对话   | 一个 tab            | 全局输入法                    |
| 导航   | 对话/家务/记账/报饭 | Today/事务/记账/家庭          |
| 数据   | 两个 tab 假数据     | 单一事实源，处处同源          |
| 主动性 | 无                  | 通知层（提醒/催办/预警/周报） |
| 撤销   | 悬在卡片上          | 撤销中心                      |
| 管理   | 家人端有死链设置页  | 与 admin 彻底分离             |
| 缺口   | 不存在              | 一等设计语言                  |

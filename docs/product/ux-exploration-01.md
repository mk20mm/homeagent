# UX 设计探索 · 第 1 轮：记账闭环与「对话—页面孤岛」

> 对齐 **AI-STD-002（AI 产品需求标准）**。

> 角色：高级产品经理 + UX 交互设计师。目标不是加功能，是让**用户需要想的越来越少**。
> 依据：2026-09-17 真机端到端走查（Playwright 全流程 + 异常制造 + 20 张截图 + VLM 分析 + 数据库交叉验证）。
> 本轮**不改代码**，只探索设计空间。

---

## 一、核心用户与核心任务

| 维度         | 结论                                                                                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 用户         | 一个家庭的 3 类成员：家长（爸爸，记账/派任务/管理）、老人（奶奶，报饭/家务为主）、孩子（受限权限）。**非技术人员，手机为主设备，每天高频、短时、碎片化使用。** |
| 核心任务     | 「说一句话，把家务/用餐/账单/日程办到位」——产品价值主张就写在登录页副标题：「登录后即可让 Agent 跑腿」                                                         |
| 真正的困难   | ① 懒得打开 App 打字记账 ② 记完没人核对，错了就错了 ③ 做饭的人不知道几个人吃 ④ 家务推给谁、谁做了不清楚                                                         |
| 产品当前阶段 | 对话记账闭环已跑通（真机验证：说「买菜花了30元」→ 入库 ¥30 → 撤销生效）。家务/报饭/设置三个页面是**静态骨架数据**，与对话不联动。                              |

---

## 二、最重要的 4 条用户流程（走查实测）

**流程 A · 记账闭环（核心路径，已通）**
打开 → 登录 → 首页自动恢复最近会话 → 输入「今天买菜花了 30 元」→ AI 流式回复 +「执行结果」卡片（含金额/类目/撤销按钮）→ 点撤销 → 卡片变「已撤销」→ 记账页显示本月汇总。
✅ 数据库交叉验证：¥30 入库且撤销后 `deleted_at` 已置位。闭环真实成立。

**流程 B · 报饭（断头路）**
报饭页 → 「在家吃/不在家吃」按钮 → **只改本地组件状态，不存后端，刷新即丢**；家人列表是写死的假数据。对话里说「今晚不回家吃」**不会**同步到报饭页。

**流程 C · 家务（断头路）**
家务页 → 3 条假数据（洗碗/倒垃圾/大扫除）→ 点「打卡」**按钮没有任何 onClick，点了无反应**。对话里说「提醒媳妇洗碗」不会在家务页出现任务。

**流程 D · 会话管理（已通）**
侧边栏 → 新建/切换（自动加载历史）/删除（confirm + 软删除）。

**横向发现：设置页（/settings）在底部 Tab 栏没有入口**，只能手敲 URL 进入；进去后所有「配置 →」「权限 →」「查看 →」都是纯文本，点击无反应。

## 三、走查发现的关键体验断点

| #   | 断点                                   | 用户在做什么                      | 实际发生                                                              |
| --- | -------------------------------------- | --------------------------------- | --------------------------------------------------------------------- |
| 1   | 首次登录不知「登录令牌」为何物         | 新用户打开登录页                  | 页面没有任何说明、没有获取入口。用户会直接放弃                        |
| 2   | 错误令牌提示「登录已过期，请重新登录」 | 输错令牌点登录                    | 首次登录的人看到「已过期」完全懵——从没登录过何来过期                  |
| 3   | 空状态示例不可点                       | 新建对话看引导「今天买菜花了120」 | 只是灰色文字，不能点。用户必须逐字手打                                |
| 4   | 记账页只显示最近几条，无「加载更多」   | 翻账本找上周一笔                  | 本月 ¥689.79 只见 ¥299，剩余约 ¥390 的记录**没有任何入口可达**        |
| 5   | 记账成功后无快速纠错                   | AI 把「花了 12」记成 ¥12          | 只能整笔撤销再重说，不能直接改金额/类目                               |
| 6   | 会话标题是首条消息截断                 | 找上周的对话                      | 标题重复（多个「买水果花了88」）、无最后消息预览、超 20 条无加载更多  |
| 7   | 家务页「打卡」点了没反应               | 完成家务去打卡                    | 无任何反馈，用户以为坏了                                              |
| 8   | 报饭页切换不保存                       | 申报今晚不在家吃                  | 切换后刷新页面状态丢失                                                |
| 9   | 设置页无入口且全是死链接               | 想换模型/退出登录                 | 只能靠「退出登录」（唯一真实功能）                                    |
| 10  | 401 控制台报错                         | 正常使用                          | 错误令牌登录在浏览器 console 留下 401（本身无害，但提示错误处理粗放） |

## 四、五个最值得探索的产品机会

> 每个机会按：用户场景 → 当前问题 → 设计洞察 → 参考模式 → 方案 A/B/C → 推荐探索 → 验证方式

---

### 机会 1：记账路径太重——「说一句话」对高频场景是负担

**用户场景**：爸爸每天买完菜，站着、单手、10 秒内想记一笔。

**当前问题**：必须「打开 App → 对话页 → 打完整句子 → 等 AI 流式回复 → 看卡片确认」。每天 3–5 次，每次都要组织语言、等回复。AI 偶尔还会理解错（把「12 块」识别成别的）。

**设计洞察**：对话是**低频复杂任务**的好入口（派任务、查预算），但记账是**高频结构化任务**——它不需要对话，需要的是「打开即输金额」。当前把两类任务压进同一个重交互，高频方被拖累。

**参考设计模式**：

- **鲨鱼记账 / 随手记**：打开就是数字键盘，输金额→选分类→完成，3 秒一笔。
- **Notion quick add**：全局快捷输入，不跳页面。
- **Linear Command Palette**：⌘K 随时呼出，自然语言 + 结构化混合。

**方案 A：保守优化——记账页加「记一笔」浮动按钮**
在记账页右下角加 FAB，点击展开金额输入（数字键盘）+ 分类自动推断，直接调后端记账接口（复用已有 `POST /expenses` 能力），不必走对话。

- 体验：高频路径从「打字说一句」变「输数字」，省 80% 输入。
- 成本：低，后端接口已存在。
- 影响：记账页从「只读账本」变成「可写」。

**方案 B：体验优化——记账成功后对话卡片加「改金额/改类目」行内编辑**
记账卡片不只给「撤销」，还给出金额和类目的可点击修正入口（Inline Edit），改完直接 PATCH。

- 体验：错了不用撤销重说，点一下改掉。
- 成本：中，需新增 PATCH /expenses/{id}。

**方案 C：重新思考——把记账页变成「家庭账本」主舞台，对话降为智能输入法**
记账页承担全部记账能力：今日概览、快速记一笔、分类筛选、日期分组；对话里说「买菜30」时，结果卡片带「在账本中查看」一键跳转并高亮该笔。

- 体验：对话是「说」，账本是「管」，各司其职。
- 成本：高，需重构记账页信息架构。

**推荐探索**：**方案 A + B 组合**先做原型。A 解决高频输入（每天 3 次的痛点），B 解决纠错（偶发但高焦虑）。C 作为长期方向。

**验证方式**：原型可用性测试——给 3 位真实家庭成员，测「记一笔平均耗时」和「纠错成功率」，对比当前对话路径。

### 机会 2：对话与三个 Tab 是「信息孤岛」

**用户场景**：爸爸在对话里说「今晚不回家吃」，然后打开报饭页想确认；或在对话里派了「提醒媳妇洗碗」，然后去家务页看。

**当前问题**：对话里做的事，页面看不到——报饭页是假数据、家务页是假数据且打卡无响应。用户会认为「刚才白说了」，对产品的信任直接崩塌。这是当前最大的**可信度风险**。

**设计洞察**：用户心里只有一个「家事本子」，不在乎是说的还是点的。任何「说了但页面不变」都是 bug 级体验。工具执行（记账）已经联动了记账页，这个模式应当扩展到家务/报饭。

**参考设计模式**：

- **GitHub Actions / Sentry**：任务执行有统一的状态流（queued → running → success/failed），跨视图一致。
- **微信接龙 / 群投票**：报饭本质是「群内收集一个状态」，接龙模式最自然——一人发起，家人逐个报，汇总实时可见。

**方案 A：保守优化——报饭先通真实接口**
报饭页接 `GET/POST /meals`：我的申报真实落库，「家人申报」列表实时拉取，未报者显示「未申报」灰态。对话里说「今晚不回家吃」调用报饭工具后，报饭页自动同步。

- 体验：解决了「刷新即丢」和「不同步」两个断点。
- 成本：中，需补报饭后端能力（当前仅有工具层，缺查询/列表接口）。

**方案 B：体验优化——家务任务流补齐**
家务页接 `GET /tasks`（我的任务/家庭任务），打卡调 `POST /tasks/{id}/done`；对话派任务后任务出现在家务页，带状态流转和积分。打卡按钮加成功反馈（轻提示 + 积分 +1）。

- 体验：家务闭环成立，「点了没反应」消失。
- 成本：中高，任务后端需补。

**方案 C：重新思考——统一「家庭动态流」**
首页对话区上方加一条「今天动态」：谁报了饭、谁完成了家务、记了多少钱。所有 tab 共享同一份领域数据，对话只是修改数据的手段之一。

- 体验：家庭协作感（互相看见），而非孤立工具。
- 成本：高。

**推荐探索**：**方案 A 优先**（报饭是最高频且最容易闭环的：就两个状态），家务（B）其次。

**验证方式**：跑流程 B 走查——对话说「今晚不回家吃」后切到报饭页，状态是否已同步；刷新是否保留。

### 机会 3：新用户第一面墙——登录令牌无解

**用户场景**：家庭新成员（比如奶奶）第一次打开，子女发的链接。

**当前问题**：登录页两个输入框「成员名（如：爸爸）」「登录令牌」。令牌是什么？从哪来？页面零说明。更糟的是输错令牌，提示「登录已过期，请重新登录」——从没登录过的人看到这个会彻底懵。VLM 走查也独立指出这是「核心缺陷」。

**设计洞察**：家庭自用产品的登录不该是「凭证墙」，而该是「邀请」。当前设计把内部安全模型（预共享令牌）直接暴露给用户，没有翻译成用户语言。

**参考设计模式**：

- **家庭组产品（Google Family / Apple 家庭共享）**：邀请制——家长生成邀请链接/二维码，成员点击即加入，无需输入令牌。
- **Slack workspace 加入**：链接邀请 + 管理员审批。
- **银行/政务类**：输入框旁的「这是什么？」问号解释。

**方案 A：保守优化——令牌输入框加说明 + 错误提示改文案**
输入框下方加小字「令牌由家庭管理员在系统管理中生成」；错误码区分「令牌错误」（提示「令牌不正确，请联系管理员」）与「会话过期」（仅在已登录态失效时出现）。

- 体验：消除「已过期」的误导；告知获取路径。
- 成本：极低（文案 + 后端错误码区分，后端已有 `apperr.Code` 枚举可承载）。

**方案 B：体验优化——管理员生成「邀请」**
设置页（家长）新增「邀请成员」：选角色 → 生成令牌 + 二维码 → 截图发给家人。成员扫码/点链接直接进登录页并自动填好成员名，只需确认。

- 体验：从「输入令牌」变成「扫码加入」，老人也能用。
- 成本：中，需后端发令牌接口 + 前端二维码。

**方案 C：重新思考——家庭成员选择即登录**
首次打开展示「这是谁？」成员头像列表（姓名由管理员预置），选人后输 4 位数字口令（而非长令牌）。安全强度足够家庭场景，记忆成本接近零。

- 体验：老人不用记长串令牌。
- 成本：中，需改认证流（短口令 + 成员预置）。

**推荐探索**：**方案 A 立刻做**（文案级修复，0 风险），**方案 B 做原型验证**（邀请制是家庭产品的标准答案）。

**验证方式**：找一个没见过产品的人实测登录——看 ta 是否能不求助地完成；观察错误文案是否造成困惑。

### 机会 4：记账成功后缺「确认—纠错」闭环

**用户场景**：说「今天买菜花了 120」，AI 记成 ¥120 食材类。

**当前问题**：结果卡片显示成功，但用户对「AI 有没有理解对」始终有疑虑（尤其老人/孩子，或口语化输入如「花了十来块」）。当前只有事后撤销（24h 窗口），且撤销是整笔删除——不能「只改金额」。走查中发现 AI 回复「需要撤销的话说一声」，但**对话里说「撤销」LLM 并没有工具可调**（技术债 T-e2e-2），只能找卡片上的按钮。

**设计洞察**：AI 产品的信任来自「可核对 + 可纠错」。每给用户一个 AI 决策，就必须配一个低成本的人工修正通道。撤销是删，修正才是改。

**参考设计模式**：

- **GitHub PR**：Review 可以「approve」或「request changes」（局部改），不是只能整个关掉。
- **Gmail「发送确认」/ 超时撤回**：操作后给一个短窗口的反悔机制。
- **银行的交易明细**：每笔可点开看详情、可申诉。

**方案 A：保守优化——卡片加「修正」入口**
结果卡片除「撤销」外加「改金额」「改类目」（Inline Edit），确认即 PATCH。保留 24h 撤销窗口作为兜底。

- 体验：错了改一下，10 秒搞定，不用整笔重来。
- 成本：低-中（需 PATCH /expenses/{id}）。

**方案 B：体验优化——「待确认」态**
高风险记账（金额异常大 / 口语化歧义如「十来块」）先不入库，卡片显示「识别为 ¥120 食材，对吗？」带「对/不对」按钮。确认后才落库。

- 体验：把纠错前移到错误发生之前。
- 成本：中（需风控阈值 + 两阶段提交）。

**方案 C：重新思考——记账卡片就是一张可编辑账单**
卡片即账单详情：金额、类目、时间、备注都可点击编辑，撤销只是其中一个动作。卡片与记账页该笔记录是同一份数据的两个视图。

- 体验：数据单一真相源，哪里改哪里生效。
- 成本：高。

**推荐探索**：**方案 A**（补「改」的能力，与机会 1 的 B 天然合并成一个 PATCH 能力），**方案 B** 作为金额识别置信度低时的增强。

**验证方式**：故意说「花了十来块」「花了 12」这类歧义输入，看修正路径是否比「撤销重说」更快、更少挫败。

### 机会 5：报饭缺「未报者」闭环——做饭的人还是不知道做多少

**用户场景**：妈妈（做饭的人）下午 4 点要知道今晚几个人在家吃。

**当前问题**：报饭页只显示已报的人（还是假数据）。**关键缺失：谁还没报**——没报的人可能是忘了，也可能是不在家。做饭的人无法据此决定做多少，只能挨个问。这才是「报饭」真正的用户问题。

**设计洞察**：信息收集工具的价值不在「已收集的」，在「还缺谁的」。未完成状态本身要被显式设计和推送。

**参考设计模式**：

- **微信群接龙**：实时显示「已接龙 N 人」，谁没接一目了然。
- **Doodle / 谁有空**：参与者状态表 + 一键提醒未回复者。
- **Linear 的 review 请求**：待办状态明确，可催办。

**方案 A：保守优化——报饭页加「未申报」分区**
家人列表分两组：「今晚在家 N 人 / 不在家 N 人 / 未申报 N 人」，未申报者显式列出（灰态 + 名字）。

- 体验：做饭的人一眼知道还缺谁，可以当面问。
- 成本：低（纯展示层，数据全在后端已有）。

**方案 B：体验优化——一键提醒未报者**
未申报分区旁加「提醒一下」按钮，对未报成员发通知（App 内消息或微信）。下午 5 点自动提醒一次。

- 体验：从「做饭的挨个问」变成「系统自动催」。
- 成本：中（需通知能力，当前产品完全没有）。

**方案 C：重新思考——报饭默认按规律推断 + 例外修正**
基于历史（工作日通常在家、周三晚上有课）给每个人一个默认值，用户只需在「例外」时申报。把「每次都要报」变成「变了才报」。

- 体验：申报次数 → 每周 1–2 次（只在变化时）。
- 成本：高（需行为学习 + 推断规则）。

**推荐探索**：**方案 A 先做**（让信息完整，成本极低），**方案 B** 在产品有通知能力后接上（这是真正的「惊喜点」：做饭的人会发现「它替我催好了」）。

**验证方式**：观察做饭的人决策时长——「未申报」分区出现后，是否还需要挨个问人。

## 五、本轮惊喜点候选（用户没说，但用了会爽）

| 惊喜点                                            | 依据                                                 | 为什么适合本产品                                        |
| ------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------- |
| **记账页「刚刚记的」置顶高亮 + 对话卡片一键定位** | 走查发现对话与账本是两个视图，切过去找不到刚记的那笔 | 强化「说一句就办了」的闭环感，信任 +1                   |
| **报饭的「例外申报」模式**                        | 机会 5-C                                             | 把高频申报变成低频，符合「用户想的越来越少」            |

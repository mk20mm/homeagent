## 0. 给执行 AI 的第一条指令

**先核对，再修改；先让现有能力闭环，再增加新能力。** 首轮禁止重写聊天、记账、家务、用餐、权限、通知或调度器，禁止擅自进入 B/C/D 阶段。必须提交代码审计摘要、改动计划、增量实现、自动化测试与端到端证据。发现关键隐私边界不清、现有数据模型不支持所需行为，先记录阻塞并提出最小修正方案，不得凭猜测扩大数据可见范围。

## 1. 产品决策摘要

**定位：** 以个人为中心、能够持续跟进家庭生活事务的 AI 代理人。对话是提出需求与处理事项的入口；Today 汇总用户当天需要关注的个人及被授权的家庭事务；已有业务页面承载查看、编辑与结果核对。三者必须指向同一业务事实。

**本期承诺的用户价值：** 打开产品知道今天与自己有关的事项；一句话创建的事务可以被找到、查看、修改或撤销（依现有业务约束）；同一事务的状态在对话、Today、业务页面和通知之间一致。

**本期不承诺：** AI 自动判断个人习惯、替家人自动分配任务、自动读微信群、系统通知一定能唤起未打开 App 的用户、家庭所有成员共享全部个人数据、医疗或财务代办。

**成功标准：** 以基线版本和改造版本完成同一任务进行对照：核心事务能够完成，关键状态一致，用户不必反复询问或跨多个入口寻找既有事务；同时不得出现隐私越权或错误的成功反馈。实际省时、省心程度须后续用真实家庭测试验证。

## 2. 现状基线与不可破坏资产

### 2.1 已存在并应复用

- ChatPage + useSSE + POST /chat：SSE 对话；ReAct runtime 与 13 个工具；quick chips、会话管理、模型选择与通知角标。
- 记账：对话与页面记账、结构化结果卡片、PATCH /expenses/{id}、?focus= 定位、流水筛选与加载、24 小时撤销；作为跨入口体验的**参考实现**，不是本期重写对象。
- 家务：assign_task / POST /tasks、任务列表、pending → in_progress → done、误打卡回退、到期通知。
- 用餐：在家/不在家二值申报、未申报名单、缺口自动通知；当前「催办」仅复制文案，**不可在本期描述为消息已发送**。
- 日程：create_event / POST /events、重复规则查询展开、单实例跳过、private 可见性；当前缺少家庭成员端的可视入口。**修改接口与重复系列编辑语义未经核实，禁止假定已存在。**
- 底座：登录与 JWT、执行层权限校验及审计、撤销中心、事件级幂等调度、静默通知策略 ADR-006、OpenAPI 类型契约、evals 与 e2e 测试。

### 2.2 已知断点，按本期处理

- P0：今天没有统一入口；创建的日程不可直接查看和管理；家务/用餐/日程的对话结果仍可能展示原始 JSON。
- P0：对话结果与业务详情尚未全面联动；通知、事项与页面的状态有待形成可验证一致性。
- P1：通知目前仅在用户进入 App 时可见，应明确产品承诺，**不擅自改变零声音零震动策略**。
- 延后：用餐默认规则、家务周期/轮值、复制文案升级为真实催办、跨模块自动编排、个人长期偏好学习、跨成员代理协作。

## 3. 目标用户、关键任务与边界

**本期首要用户：** 已加入同一家庭、通过个人身份登录、使用对话或页面管理个人和被授权共同事务的成年成员。长辈和未成年人的独立使用流程不在本期新增；现有功能不得退化。

**核心任务 T1：** 用户今天打开产品，快速识别与自己有关的日程、未完成任务、用餐确认状态及需处理的通知，并进入具体事务。

**核心任务 T2：** 用户通过对话创建一条日程，得到人类可读的成功反馈，可从结果到详情、从 Today 到详情；需要修改/取消时，系统只提供仓库核实后支持的操作。

**核心任务 T3：** 用户通过对话完成家务或用餐操作后，收到可读、准确的结果和相关入口，不再看到原始 JSON；刷新、跨页查看时状态一致。

**核心任务 T4：** 用户撤销、取消或修改一个允许变更的事项后，Today / 详情 / 对话中后续查询与通知相关状态不互相矛盾。

**信息边界：** 个人信息只展示给有权查看的人；共同事务按现有服务端权限规则展示。现有「家庭共享」不等于所有人的个人日程、个人账单或私人对话都可公开。汇总和深链跳转都必须调用服务端授权，不能仅靠前端隐藏。

## 4. 本期信息与行动组织原则（不预设视觉稿）

1. Today 是用户**今天的行动摘要**，而不是所有模块的完整看板；优先显示「需要我处理」与「今日安排」，其次显示「家庭用餐简况」与「代理人动态」。
2. 对话仍是可随时抵达的核心入口，不因 Today 设为首次进入入口而被深藏；用户可以快速进入新对话、已有会话与常用操作。
3. 具体业务页面是可查可改的事实承载位置；Today 与对话结果不创建第二份事项，也不自行维护独立完成状态。
4. 「已完成」「等待他人回应」「尚未申报」「按默认计划预计」必须是不同含义。本期不存在用餐默认计划，不得擅自将未申报转为已确认。
5. 系统只对**确认成功的持久化操作**展示成功态；创建失败、参数不完整、未授权和通知仅已入库的情况必须准确表达。
6. 无数据是正常状态：Today 空态需明确「今天没有需要你处理的事项」，并允许用户开始对话，不制造任务或虚假警报。

## 5. V1.0-A 需求清单与实施顺序

### A-00｜代码与行为基线复核（硬性前置）

**目标：** 在修改之前建立现状证据和回归保护。

- A-00-01 查明实际路由、Tab、Today/日程的现存实现、ChatPage 卡片渲染分支、业务接口契约与服务端权限实现。将用户提供的功能清单标为「核实」「部分核实」「不符」。
- A-00-02 对四条当前流程完成一次基线走查：对话记账、家务打卡、用餐申报、对话创建日程及后续查询。保留测试步骤、截图/日志或可重复测试记录。
- A-00-03 查明事件详情/更新/取消接口是否已有；重复系列是只支持删除单次，还是支持修改单次/修改全系列。查明撤销中心实际支持哪些写操作与 24h 限制。
- A-00-04 列出前端组件与路由、服务端接口和测试改动清单。**若关键权限不可确认，暂停对该信息的 Today 展示。**

**完成定义：** 输出 `docs/exec-plans/active/family-agent-v1a-audit.md`（若仓库已有约定路径则沿用）和基线结果，不凭本文推测替代代码事实。

### A-01｜Today：个人今日行动摘要（P0）

**用户故事：** 作为家庭成员，我希望进入产品后快速知道今天与我有关的安排、需要处理的事情与已经得到的结果，不必挨个打开各模块或重新询问 AI。

**最小需求：**

- A-01-01 展示「需要我处理」：来自现有可授权读取的数据，至少覆盖我的未完成且需处理的任务、我尚未申报的当日用餐（如适用），以及真正需要回应/确认的通知；仅未读但无需操作的普通消息不混入强行动区。
- A-01-02 展示「今日安排」：当天可见日程，包含时间、标题和必要状态；私密日程严格依创建人及现有服务端权限规则。跨天/重复日程是否展示须以现有业务语义及测试为准。
- A-01-03 展示简洁的家庭用餐概览与我自己的状态；「在家 / 不在家 / 未申报」原样保留，不将未申报写成不在家。
- A-01-04 展示有限条与我相关的代理人/通知动态；已入库通知≠用户实际已看到，已读≠实际事务已完成。
- A-01-05 每项可操作内容具备进入对应详情或原有操作的路径；执行完成、取消、撤销后重新获取单一事实源并更新相关区域。
- A-01-06 在零条、加载中、局部接口失败、已过期事件等状态下提供准确反馈；某个模块失败不能让其他有效模块变成「今天没有事」。

**不做：** 重新实现一份任务表；家庭成员所有私人数据大汇总；天气、新闻、菜谱推荐；预算报表全量复制；大语言模型凭空生成 Today 业务事实。

**验收：** 当天个人日程、任务和用餐状态从已存在业务数据准确汇总；无权用户看不到对应信息；点击可到正确对象；变更后的刷新结果正确。Today 可以使用专门的只读聚合接口，也可在遵守现有契约前提下复用现有读接口，由执行代理根据仓库实况选择，不要求新建数据源。

### A-02｜日程可见、可查看、可安全管理（P0）

**用户故事：** 作为创建日程的成员，我希望在对话外找到日程、查看详情，并按既有业务规则修改或取消它。

**最小需求：**

- A-02-01 存在可从主要导航或 Today 抵达的日程入口；最小实现为日期范围的日程列表及详情，**不要求复杂月历/拖拽视图**。
- A-02-02 对话成功创建事件后，返回稳定的事件标识，并提供直接进入相应详情的路径；若实际协议没有事件 ID，先完成契约核实再增量补齐。
- A-02-03 日程详情展示标题、时间、重复/单次属性、相关可见性和可执行操作；各字段仅显示已核实的值。
- A-02-04 修改与取消：先检查现有接口与领域语义。若缺少必要写接口，按最小兼容方案补齐；**不得把“取消一次”误实现为删除整个系列，也不得承诺不存在的“修改整系列”能力**。
- A-02-05 对重复实例执行编辑/取消前，明确告知作用范围；无权限、已不存在、同时被修改、无效日期与重复冲突等情况给出准确反馈。
- A-02-06 Today / 日程 / 对话后续查询以相同可见性和重复展开语义读取；私密日程不得在家庭汇总或深链中泄露。

**范围决策：** 如果现有后端仅支持“单实例跳过”，本期必须先支持准确查看与已有取消操作；修改单次/整系列若需要大规模领域重构，记录独立缺口并按风险决策，不允许为了达成表面“可编辑”破坏现有重复规则。

**验收：** 创建→结果卡片→日程详情→Today 显示一致；单次跳过只影响目标实例；他人无权访问私密日程，即使持有详情链接也返回受控的无权限/不存在响应。

### A-03｜对话结构化结果与操作联动（P0）

**用户故事：** 当我让代理人记一笔账、创建日程、报饭或安排家务时，我能够明确知道完成了什么，以及在哪里继续查看或更正。

**最小需求：**

- A-03-01 保留现有 expense 结果卡片与修正/定位/撤销能力，抽取可复用的状态表达原则，但不重写已稳定的记账领域逻辑。
- A-03-02 task、meal、event 类型不直接向最终用户展示 `JSON.stringify(card)` 原始结构；至少展示人类可读的动作、对象、关键参数、真实执行状态和可进行的下一步。
- A-03-03 工具执行成功但需要他人回应时，仅表述为「请求已发送/等待回应」（须实际存在真实发送机制才允许此文案）；本期复制提醒文案仅表达为「已复制，尚未发送」。
- A-03-04 对话结果中进入详情的入口必须携带稳定对象定位信息；目标已删除、已撤销、无权限时不能跳到错对象或展示过期成功态。
- A-03-05 错误或部分成功的工具执行必须区分失败原因与可执行的恢复动作；不把 LLM 的自然语言保证当作真实业务成功。

**验收：** 人工和自动化检查无 raw JSON 面向用户展示；对各模块成功、失败、撤销、权限不足、重复提交至少有对应状态测试；已修复的快捷 chips、欢迎页示例、记账快捷纠错不退化。

### A-04｜跨入口状态一致与通知语义（P0/P1）

**用户故事：** 我在任一入口变更了事项，在其他入口看到的应是同一事实；收到通知时能分清信息、待处理与真正完成。

**最小需求：**

- A-04-01 定义轻量的前端刷新/失效约定：创建、更新、取消、撤销、完成后使 Today、相应详情及计数从业务源重新获得正确结果，不能仅改一处 UI 的本地假状态。
- A-04-02 标识通知的「未读/已读」与关联事务的「待处理/已完成」是两条不同状态；阅读通知不能自动完成任务，任务完成后不能继续将其显示为待执行。
- A-04-03 保留事件级幂等及现有静默策略；本期不擅自开启声音、震动、系统级推送，不声称 App 关闭时一定及时提醒。
- A-04-04 Today / 通知中心在局部失败或网络重试时避免重复显示同一通知为多项任务；对象不存在时给出明确而安全的反馈。

**验收：** 同一用户在对话、Today 和业务页面操作后，无需手工清除缓存即可看到一致结果；刷新不重复写业务数据；撤销窗口与服务端真实规则一致。

### A-05｜权限与敏感数据边界（跨所有 P0）

- A-05-01 为 Today 每个数据来源建立主体、对象归属、可见范围的最小权限矩阵；沿用现有服务端执行层校验，不以 prompt 过滤或前端隐藏代替授权。
- A-05-02 私人日程遵守 private 仅创建人可见的既有规则；个人账单如果当前为共享模式，**本期不自行宣布其已私密**，先核实现有授权语义，再限定 Today 展示范围并记录后续数据归属改造议题。
- A-05-03 家务任务涉及别的成员时，本期保持既有任务业务语义，不悄悄增加“对方已同意”的表述。真正的协助请求/接受拒绝属于阶段 C。
- A-05-04 对已有深链、聚合接口、通知附带对象 ID 进行越权验证；跨用户链接不可暴露对象标题、金额、备注等敏感信息。

**阻塞规则：** 如现有接口无法区分有权/无权数据，先修正最小权限漏洞或屏蔽对应 Today 条目，并向负责人报告，不得为了交付首页绕过权限。

## 6. 最小用户旅程与端到端验收

### E2E-01｜打开 Today

前置：同一用户有今日个人日程、未完成任务、今日用餐未申报和一条普通未读通知。操作：登录进入默认入口 → 查看 Today → 进入任务详情完成。预期：显示今日安排与需处理事项；普通通知不冒充待办；任务完成后从待处理区消失或显示已完成，原家务页状态一致。

### E2E-02｜对话创建并查看日程

操作：对话「下周三下午三点开家长会」→ 获得成功结果 → 进入日程详情 → 查看对应日期。预期：只有服务端确认后显示成功；结果卡片无原始 JSON；标题时间一致；同一事件在日程页与 Today（若对应当天）可被找到。

### E2E-03｜重复日程仅跳过一次

前置：存在按周重复日程。操作：查看某次实例 → 选择只取消这一次 → 查看后续实例。预期：目标实例不再出现或按现有语义标记跳过；后续实例继续存在；不存在误删整系列。

### E2E-04｜跨成员私密日程

前置：成员 A 创建 private 日程；成员 B 同家庭。操作：B 查看 Today/日程列表，并尝试打开 A 的对象深链。预期：B 看不到私人事项内容，服务端拒绝越权；A 正常查看。

### E2E-05｜家务与用餐结果反馈

操作：对话创建/完成一项家务、申报今晚不在家吃饭，查看结果卡片、对应页面与 Today。预期：无 raw JSON；对象与真实结果可核对；报饭三态语义不变；不存在「催办消息已发送」的错误表述。

### E2E-06｜撤销、失败、重试

前置：分别准备可撤销写操作、过期撤销、无权限访问与模拟网络中断。操作：撤销/重试/刷新。预期：受支持的撤销改变业务事实并同步页面；超过真实期限正确拒绝；无权限不泄露详情；失败不显示成功；重试不造成重复业务记录。

### E2E-07｜核心功能回归

覆盖已稳定流程：对话记账/手动记账/改账/撤销/定位/筛选和加载；家务两步打卡与回退；用餐二值幂等与缺口汇总；聊天 SSE、会话切换、快捷 chips、通知中心与静默策略。现有回归基线不得下降；如果出现失败，定位并修复后再交付。

## 7. 产品价值验证方法

**功能完成不等于价值兑现。** 建议在现有版本和 V1.0-A 中，用相同角色与同一任务比较以下指标；先采集基线，不设没有依据的绝对提升百分比。

| 验证问题 | 观测指标 | 通过依据 |
|---|---|---|
| 今天有什么需要处理？ | 找到当天关键事项所需步骤/时间、漏看率 | 可在 Today 正确找到事项，关键状态无遗漏、无越权 |
| 创建的日程能否再次找到？ | 从创建结果到详情的成功率、操作步骤 | 能直接定位且日期/可见性准确 |
| 代理人做成了什么？ | 成功/失败/待确认的识别正确率 | 结果文案与服务端事实一致，无 raw JSON |
| 一处操作后，其他地方会不会变？ | 跨入口状态不一致次数 | 所有验收场景中无已知不一致 |
| 是否真正省心？ | 真实家庭用户主观负担、重复查询/操作次数 | 进入小规模实际使用验证后再定量判断，不能凭开发自测宣称成立 |

不把「29 条 eval 全过」「35/35 e2e」视为体验改善的直接证据；它们是已报告的工程基线，须在当前仓库重新运行复核。

## 8. 版本拆分、任务依赖与交付闸门

**提交 0｜核实与基线：** 完成 A-00；明确路由、接口、重复日程语义、权限和测试命令。未通过不得进入实现。

**提交 1｜日程可查：** A-02 的入口、列表、详情和已有操作；补齐必要且最小的后端契约。涉及重复规则的危险写操作单独提交，先测试后开放。

**提交 2｜结果卡片：** A-03，优先 task / meal / event；保留 expense 原有表现；建立成功/失败/待确认文案规范。

**提交 3｜Today：** A-01，复用已核实的日程/任务/用餐/通知事实；同时完成 A-05 对应数据的权限验证。

**提交 4｜联动与回归：** A-04，完成跨入口更新、通知语义、异常及 E2E-01~07；提供真实屏幕走查或可重复测试记录。

以上是逻辑提交顺序；如果仓库依赖要求局部调整，应在执行计划中说明理由，不改变产品范围与验收条件。

**交付闸门 G1（事实）：** 不存在伪造成功、不存在错误的已发送/已确认表述。  
**G2（安全）：** 私人/跨成员数据不因 Today、深链或通知被公开；关键越权测试通过。  
**G3（闭环）：** 对话创建→详情查看→业务变更→Today/其他入口刷新结果一致。  
**G4（质量）：** 相关单测、集成测试、现有 eval/e2e/go test 等依仓库命令通过；若环境阻塞须披露，不能虚报通过。  
**G5（证据）：** 每项需求有代码改动、测试用例或可重复人工验证步骤及最终差异说明。

## 9. 风险、约束与停止条件

- **权限风险：** 当前只有日程 private 规则被明确说明；不要推断其他模块已个人隔离。遇到越权隐患先修复或屏蔽，不得通过前端条件渲染掩盖。
- **重复日程风险：** “查询时展开”和“单实例跳过”不能自然推出支持完整系列编辑；先核对再决定本期最小写操作。
- **通知风险：** ADR-006 规定静默；不得将站内入库通知描述为用户在后台已获知。推送策略更改须另起产品决策。
- **家务语义风险：** 当前 assign_task 是既有任务能力，不代表接收人同意。本期不暗改任务状态机来模拟家庭协作。
- **记账风险：** 24h 撤销、同日同额同内容幂等及真实历史流水要保留；不把记账当作新领域进行重写。
- **产品范围风险：** 如需要大规模数据库迁移、权限体系重构、跨成员代理协议、新增生活领域，先形成变更单及取舍，不自动纳入本期。

## 11. 执行 AI 最终交付格式

1. **审计摘要：** 用户给出的现状哪些与仓库一致，哪些不一致；已复用与新增的能力；未解决限制。
2. **需求映射：** A-00～A-05 每一项对应代码文件、接口/状态语义、测试用例与实施结果。
3. **变更清单：** 明确新增/修改的路由、组件、API、契约、领域规则与数据变更；未做的内容说明原因。
4. **验证记录：** 实际执行命令及结果；E2E-01～07 的通过/失败情况；失败必须写清楚，不得删去失败用例粉饰结果。
5. **体验走查：** 按「打开 Today→发现事项→对话操作→查看详情→修改/撤销→回到 Today」完整展示可复现步骤。
6. **阻塞与后续：** 仅列实际发现的阻塞、风险和 B/C/D 候选议题，不扩大本期需求。

# 家事 Agent · 产品灵感与四模块深耕研究（第一版）

> 角色：产品战略 + 产品经理 + AI 产品设计。
> 对齐 **AI-STD-002（AI 产品需求标准）**：本文为 `AI-PRD.md §10` 提供模块深度标尺（L0–L4），需求以 §10 为准。
> 命题：**这个产品是家庭事务中枢，不是记账应用。** 第一版四模块（家务 / 用餐 / 账单 / 日程）全景铺开，但每个模块必须深耕到市场可用线以上——不是每个都浅一层。
> 方法：先看市面同类软件在每个模块做到什么程度（能力面而非功能点），再回推**我们必须做到的最低线**与**能做出差异化的地方**。
> 上游：[`product-design-research-01.md`](product-design-research-01.md)（理念、原则 8 条、IA、交互系统、演进路线）｜下游：功能与交互方案 → 开发。
> 范围：本轮不改代码、不改契约。新增/前移的契约与 ADR 需求登记在 §7，与研究报告附录 A 的 C 编号连续。

## 0. 本轮结论（先给判断）

| #      | 判断                                                                                                                                                                                                                                                                         | 依据 |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| **I1** | 市面产品**没有一个**同时做到"对话即录入 + 四模块同源 + 主动提醒"。家庭中枢类（Cozi / FamilyWall / Skylight）做的是**看板与共享**，把入口交给用户点；专项类（Tody / AnyList / 钱迹）做的是**单模块深耕**，不跨模块。**我们的空位是"入口成本 + 跨模块 + 主动性"三者叠加**。    | §2   |
| **I2** | 四个模块在市场上都有成熟的**深耕标尺**可对齐：家务看 Tody 的"dueness + 把提醒与记分搬进系统"、用餐看 AnyList 的"菜谱→清单→菜单闭环"，账单看钱迹的"日期分组 + 周期账单 + 多维搜索"，日程看 Cozi/TimeTree 的"成员颜色 + 提醒 + 当日议程"。**这些是 V1 的最低线，不是加分项。** | §3   |
| **I3** | "每个模块深耕"与"四模块全景"会**改关键路径**：日程模块（提醒/周期/农历）依赖通知与调度底座，因此**主动服务底座必须从 Phase 2 提前到 V1 阶段 A**（研究报告 C4/C5 前移）。不提前，日程模块只能做成"看日历"，等于没深耕。                                                       | §6.4 |
| **I4** | "Today = 当日议程一屏"不是我方独创，Cozi Today 与 Skylight 都验证了这个形态；**我们的差异化不在这一屏，而在这一屏的内容可以由一句话生成、且缺口（未申报/未打卡/未认领）在其中显式出现**。                                                                                    | §3.5 |

## 1. 定位校正（本轮最重要的前提）

| 维度       | 错误定位（要避免）       | 正确地位（V1 起必须成立）                                                          |
| ---------- | ------------------------ | ---------------------------------------------------------------------------------- |
| 产品身份   | 一个更聪明的记账 App     | **家庭事务中枢**：家务、用餐、账单、日程四个模块同权，对话是统一入口               |
| 模块关系   | 记账是主功能，其他是附属 | 四模块**同源**（同成员、同提醒、同动态流、同撤销体系），谁都不是附属               |
| 首页       | 账本或对话               | **Today**：今天的饭、今天的事、这个月的钱、今天家里发生了什么                      |
| 成功的标志 | 记账笔数                 | **四模块都有真实使用**：有人报饭、有人打卡、有人记账、有日程被提醒到               |
| 扩展方式   | 加页面                   | 加模块 = 权限矩阵加一列 + 工具注册 + Today 加一屏（`tool-perms-config.md` 已设计） |

**为什么这条校正必须落进 V1**：如果 V1 只把记账做深（现状已接近），产品就会被家人和外部认知固定成"记账工具"，之后再挂三个模块会显得是补丁——**先把中枢骨架立起来，所以四模块全景是定位选择，不是排期选择**。

## 2. 调研范围与市面产品能力面

调研对象按"与本产品解决相似问题"筛选，不局限于同类竞品。

| 类别      | 产品                             | 它解决的用户问题               | 核心设计模式                                                                                                                                        |
| --------- | -------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 家庭中枢  | **Cozi Family Organizer**        | 一家人的日程/清单/吃饭在一处   | 颜色编码共享日历 + 共享清单 + 菜谱 + **Cozi Today 当日议程一屏**                                                                                    |
| 家庭中枢  | **FamilyWall**                   | 家庭信息与沟通统一             | 日历/清单/消息/照片/文件/记账/菜单规划全塞一处，Premium 加位置共享                                                                                  |
| 家庭中枢  | **Skylight Calendar**            | 家庭看板（常驻屏，非个人手机） | 触摸屏看板 + 家务星标奖励 + 例程(routine) + 一周菜单 5 分钟规划 + **Sidekick 把邮件/PDF/纸质表变成日程**                                            |
| 家务专项  | **Tody**                         | 家里该清洁什么、多久一次       | **dueness（按需而非按日历）** + 房间/区域分解 + 每任务频率/工作量/季节性 + 家庭同步                                                                 |
| 家务专项  | **OurHome**                      | 谁该做什么、孩子怎么被驱动     | 指派（单人/多人/**轮值**）+ 到期与重复 + 逾期惩罚 + **家长审批** + 积分/奖励/零花 + 分孩权限                                                        |
| 用餐专项  | **AnyList**                      | 买菜、菜谱、菜单一条线         | 菜谱收藏/导入 → **一键进购物清单**（自动合并同类食材）→ 菜单日历 → 生成购物清单；清单自动分类、常用项优先、按店铺分区                               |
| 用餐专项  | **下厨房 / 食见集 / 下周吃什么** | 今晚吃什么、缺什么食材         | 菜谱一键加采购清单、拍照识别菜谱、一周菜单计划、时令推荐                                                                                            |
| 账单专项  | **钱迹**                         | 记完能查、能统计、少手输       | **账单按日期分组+每日小计**、点日期直接补账、**周期记账到期自动生成**、分期账单、多维搜索（金额/时间/账本/标签/分类）、微信支付宝账单 AI 导入、导出 |
| 账单专项  | **YNAB / 随手记**                | 预算约束与快速记录             | 信封预算（给每一分钱定用途）、键盘即记（3 秒一笔）                                                                                                  |
| 日程专项  | **TimeTree**                     | 多人共享日程不打架             | 共享日历 + **成员专属颜色** + 事件变更通知 + 月/周视图 + 关键词搜索 + 邀请成员                                                                      |
| 日程专项  | **Google Calendar / 系统日历**   | 提醒别漏                       | 重复规则、提前提醒阶梯、多日历叠加、iCal 订阅                                                                                                       |
| 语音/管家 | **小爱同学 / 智能家庭屏**        | 动口不动手                     | 一句话设提醒/闹钟、**主动建议**（打卡/吃药/食品保质期/纪念日）、定时提醒、家庭共享设备                                                              |
| 适老      | **微信关怀模式 / 长辈模式实践**  | 老人能用                       | 字大按钮大、**默认语音交互**、方言识别、**结果需多通道确认（视觉+听觉+触觉至少一个）**、模式入口必须好找（普遍痛点是藏太深）                        |

**三条从调研里得出的硬事实**

1. **家庭中枢类的通病是"要用户点"**：Cozi/FamilyWall/Skylight 都靠用户主动打开、主动录入、主动看板。它们把信息组织得很好，但没有降低录入成本——这正是我们的入场理由（理念"省一次输入"）。
2. **专项类深耕的深度远超我们预期**：Tody 有 dueness 曲线与工作量；AnyList 有食材合并与按店铺分区；钱迹有周期账单与多维搜索。**这些不是"高级功能"，而是各自品类里"能被长期用"的门槛**。
3. **"把提醒与记分搬进系统"是被验证过的价值主张**：Tody 的原文表述是让"asking, reminding, score-keeping"从人转移到系统——与本产品"跑腿"主脉完全同源，可作为我们主动服务的设计依据。

## 3. 四模块深耕标尺

### 3.0 统一深度分级（所有模块同一把尺）

| 级别   | 名称 | 判定标准                                                           |
| ------ | ---- | ------------------------------------------------------------------ |
| **L0** | 骨架 | 页面存在，数据是假的或只有只读展示                                 |
| **L1** | 可用 | 数据真实、能录入能查看、刷新不丢                                   |
| **L2** | 完整 | 覆盖该模块高频全流程；有纠错、撤销、缺口、空态引导                 |
| **L3** | 深耕 | 有智能默认/推荐、主动提醒、统计复盘、可配置；**V1 的每模块最低线** |
| **L4** | 领先 | 跨模块联动、可学习偏好、可推荐/预测                                |

**V1 目标**：四模块 **全部 ≥ L3**，且至少有一条跨模块联动（L4 的雏形）。**不接受**"账单 L4 + 其他 L1"——那正是要避免的"记账应用"。

### 3.1 家务模块（深度目标 L3）

| 市场已做到（依据）                                                  | V1 必须有                                                                     | 我们的差异化                                                |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 按房间/区域分解任务、每任务自己的频率与工作量、dueness 排序（Tody） | **任务模板 + 频率**：常见家务带默认频率与预计耗时；"该做了"由系统算，不靠人记 | 频率不是写死的日历，而是**对话可改**（"以后每周三擦地"）    |
| 指派单人/多人/**轮值**、到期与重复、逾期惩罚、家长审批（OurHome）   | **轮值 + 指派 + 认领**：谁做、什么时候轮换；孩子任务需家长确认                | **缺口驱动**：没人认领/没人打卡时，Today 显式提示并一键催办 |
| 积分、奖励、零花/屏幕时间挂钩、目标（OurHome）                      | **积分 + 完成率**（先做可见，不做兑换商城）                                   | 积分用于**家庭内可见的公平感**，不做攀比排名                |
| 例程(routine) 与家务(chore) 区分、星标奖励（Skylight）              | **例程**（每天刷牙式固定动作）与**家务**（周期性任务）分开                    | 例程走"打卡"，家务走"派单"，交互不同（P1 逻辑）             |
| 家庭同步、贡献被记录（Tody）                                        | **完成历史可查**、误打卡可撤销                                                | 撤销也进撤销中心（已有统一出口）                            |

**V1 明确不做**：子任务/甘特图（`AI-PRD §7`）、积分兑换商城（V3）、家务外包对接。

### 3.2 用餐模块（深度目标 L3）

| 市场已做到（依据）                                           | V1 必须有                                                       | 我们的差异化                                               |
| ------------------------------------------------------------ | --------------------------------------------------------------- | ---------------------------------------------------------- |
| 报饭/人数统计——**市场上没有这个品类**                        | **报饭 + 缺口 + 催办**：今晚几人吃、还缺谁没报、一键催办        | 做饭人视角的"做多少"结论；默认按历史规律、例外才申报（P4） |
| 菜谱库 + 网页导入 + 食材一键进清单 + 自动合并同类（AnyList） | **菜谱 + 缺食材进清单**（V2 的联动，V1 至少做到手动加料进清单） | 一句话"按这个菜谱买菜"→ 自动比对库存/上次购买              |
| 一周菜单计划 + 生成购物清单 + 家庭最爱（AnyList / Skylight） | **一周菜单**（可空）+ "今晚吃啥"推荐**给依据**                  | 推荐理由必须说清（预算/库存/口味/最近没吃）                |
| 拍照识别菜谱、AI 建议新菜（Skylight Sidekick / 食见集）      | ❌ V1 不做，登记 V3（配合图片输入 ⚠️ C9）                       | 一期用"说一句"替代拍照                                     |
| 外卖记账、时令推荐                                           | 外卖记账（V3 规划）                                             | 时令推荐可作"吃啥"的一个依据维度                           |

**V1 明确不做**：外卖下单（`AI-PRD §7`）、比价、代购。

### 3.3 账单模块（深度目标 L3）

| 市场已做到（依据）                                    | V1 必须有                                                               | 我们的差异化                                       |
| ----------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------- |
| 账单**按日期分组 + 每日小计**、点日期直接补账（钱迹） | 账本按日分组 + 每日小计 + 点日期补账（补账日期自动带上）                | 已有 `?focus=` 高亮，补充"日期跳转"                |
| **周期记账**（到期自动生成）、分期账单（钱迹）        | **周期账单**（房租/水电/订阅）+ **到期进提醒中心**                      | 账单到期与日程提醒**同一个提醒中心**，不是两个 App |
| 多维搜索（金额/时间/账本/标签/分类）、导出（钱迹）    | 搜索（时间/分类/金额/内容）+ 导出 CSV（⚠️ C11）                         | 搜索可走对话（"上个月打车花了多少"）               |
| 自动导入微信/支付宝账单（钱迹）                       | ❌ V1 不做（依赖外部账单文件与解析）；登记为后续能力                    | 我们用"一句话记"替代导入                           |
| 信封预算、给每分钱定用途（YNAB）；预算超支提醒        | **分类预算 + 进度 + 超支提醒**（`query_budget` 已有工具，需页面与提醒） | 预算进度进 Today，超支主动提醒                     |
| 3 秒一笔的快速键盘（随手记/鲨鱼）                     | 已有 FAB + 修正；补"分类记忆"（上次"买菜"→食材）                        | 对话 + 键盘两条路径并存（老人/静音场景）           |

**V1 明确不做**：AA 分摊结算、投资理财、银行卡直连（`AI-PRD §7`）。

### 3.4 日程模块（深度目标 L3）

| 市场已做到（依据）                                            | V1 必须有                                                | 我们的差异化                                                   |
| ------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------- |
| 共享日历 + **成员专属颜色** + 邀请成员（TimeTree / Cozi）     | 家庭共享日历（月/周/列表）+ 成员颜色 + 我的/全家的切换   | 颜色即"谁的事"，减少家庭内部误会（对应"责任划分清楚"的实践）   |
| 提前提醒、每日 agenda 邮件、当日议程一屏（Cozi / Cozi Today） | **提醒阶梯**（提前 1 天/1 小时）+ Today 当日议程         | 提醒落在**同一个通知中心**，与账单到期、任务到点、报饭缺口并列 |
| 重复规则、多日历叠加、iCal 订阅（系统日历）                   | **重复规则**（每天/每周/每月）+ **单向 iCal 订阅**（⚠️） | iCal 让提醒进手机系统日历，漏不掉（`§8.4 V2` 已规划）          |
| 生日/纪念日倒计时（Skylight）                                 | **农历生日/纪念日提醒**（中国场景刚需）                  | Cozi/TimeTree 没有农历；这是本土化差异点                       |
| Sidekick：邮件/PDF/纸质表 → 事件（Skylight）                  | ❌ V1 不做，登记 V3（配合图片/文本解析）                 | V1 用一句话建事件代替                                          |
| 位置共享（FamilyWall Premium）                                | ❌ **不做**（隐私，且超出家庭事务范畴）                  | ——                                                             |

**V1 明确不做**：第三方日历双向同步（`§7`）、复杂协作权限、位置共享。

### 3.5 中枢层（跨模块，V1 必须成立）

| 能力             | 市场依据                                   | V1 设计                                                                                                            |
| ---------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Today 一屏**   | Cozi Today（当日议程一屏）、Skylight 看板  | 今晚吃饭（含缺口）/ 我的待办 / 本月与预算 / 当日日程 / 家庭动态                                                    |
| **统一提醒中心** | Cozi 提醒、小爱"主动建议"、Skylight 倒计时 | 一个中心收口：任务到点、日程提醒、账单到期、预算超支、报饭缺口、耗材将尽（V2）；可静音、可追溯                     |
| **家庭动态流**   | Tody"贡献被记录"、FamilyWall 消息/照片     | 谁做了什么（可撤销、可点开），替代"群里喊一声"                                                                     |
| **成员与颜色**   | TimeTree/Cozi 成员颜色                     | 成员头像色在全产品一致（日历/任务/账单归属）                                                                       |
| **共享清单**     | AnyList/OurHome/Cozi 共享购物清单          | V2 模块（⚠️ C8），但 V1 的报饭/任务页必须长成同构形态                                                              |
| **语音入口**     | 小爱、AnyList（Siri/Alexa）                | V1 不做 STT（⚠️ C9），但**把"一句话"路径做顺**；V3 接语音                                                          |
| **适老**         | 微信关怀模式、长辈模式实践                 | 大字号 + 大按钮 + 一键动作（报饭/打卡/看今天）+ 结果多通道确认；**模式入口必须在首屏可及**（调研中最普遍的失败点） |

## 4. 从调研直接得到的设计修正

| #   | 修正                                               | 依据                                            | 影响面                                   |
| --- | -------------------------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| M1  | 任务需要**频率/周期**概念（家务不是一次性待办）    | Tody 的 dueness、OurHome 的 repeating schedules | 家务模块数据模型 + 家务页 + 提醒中心     |
| M2  | 任务需要**轮值（rotation）**                       | OurHome 指派三人模式                            | 派单交互 + 任务模型                      |
| M3  | 孩子任务需要**家长审批**                           | OurHome approval                                | 打卡状态机多一态（待确认）               |
| M4  | 例程与家务**必须分开**                             | Skylight routine vs chore                       | 家务页分区 + 打卡交互差异                |
| M5  | 账单需要**周期记账**（到期自动生成）               | 钱迹周期记账                                    | 账单模块 + 调度器（与 M1 共用底座）      |
| M6  | 账本**按日分组 + 每日小计 + 点日期补账**是品类门槛 | 钱迹主界面                                      | 记账页信息架构（原 Phase 1 第 6 项扩展） |

## 6. V1 范围与影响（关键路径重排）

### 6.1 V1 的定义

**V1 = 四模块全部 ≥ L3 + 中枢骨架成立 + 主动服务可用。** 不是"记账做深、其他占位"。

### 6.2 阶段划分（相对研究报告 §15 的修订）

| 阶段                      | 内容                                                                                                                                                                                   | 相对原计划的变化                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **阶段 A · 可信度与底座** | 原 Phase 1 九项（家务/报饭真实化、撤销中心、快捷 chips、账本、文案、入口、对话侧撤销）+ **通知与调度底座（C4 ADR + C5 通知接口）**                                                     | **主动服务底座从 Phase 2 前移到阶段 A**                       |
| **阶段 B · 四模块深耕**   | 家务（频率/轮值/例程/审批/缺口催办）、用餐（报饭缺口/例外申报/菜谱→清单最小版/吃啥给依据）、账单（按日分组/搜索/周期账单/预算提醒）、日程（共享日历/成员颜色/提醒阶梯/重复/农历/iCal） | **日程模块从 Phase 4 前移到 V1**；账本项扩展为"按日分组+补账" |
| **阶段 C · 智能化**       | 智能默认、异常检测、可解释、周报、推荐给依据                                                                                                                                           | 不变（原 Phase 3）                                            |
| **阶段 D · 形态升级**     | 购物清单完整联动、跨模块联动、适老落地、语音、长期记忆                                                                                                                                 | 原 Phase 4 减去日程，加深入适老                               |

### 6.3 依赖拓扑（阶段 B 的内部顺序）

```
通知与调度底座（C4 ADR → C5 接口）
   ├──→ 家务：到期/逾期/缺口催办 · 周期任务
   ├──→ 账单：周期账单到期
   └──→ 日程：提醒阶梯 · 农历生日 · 重复规则
日程模块（C13 数据模型 + 共享日历 + 成员颜色）
   └──→ Today 当日议程
用餐：报饭缺口（依赖通知）· 菜谱→清单（依赖 C8 购物清单最小表）
账单：按日分组/搜索（纯前端 + C6 搜索接口）
```

**结论**：**通知底座是四模块深耕的唯一共同前置**。这就是 I3 判断的落地含义。

### 6.4 对 v1 节奏的直接影响（三条）

1. **先做 C4 ADR 再做通知接口**：打扰预算是产品承诺（P7），没有它就先做推送，会出现"提醒太多→全关掉→永远不再打开"的典型失败。
2. **日程模块必须先定数据模型（C13）再看日历 UI**：成员颜色、重复规则、农历、提醒阶梯四件事都落在模型上。
3. **购物清单（C8）在 V1 只做"最小表"**：只为支撑"菜谱→缺食材→清单"这条联动，不做完整囤货/耗材管理（那是 Phase D）。
